# OT 設定飄移研究計畫

更新日期：2026-09-30。研究範圍限於經授權的隔離測試床、既有檔案與被動取得的資料。

## 研究主張與邊界

本專案先回答「設備或其防護閘道的實際設定是否偏離核准基線」，再回答「變更是否經核准」及「是否有可觀察的網路或製程後果」。這三個判斷應保留各自的證據和不確定性。設定已變更但製程尚無異常，仍是設定事件；製程異常也不能反推設定被改動。

應把欄位語意定義到具體控制點。例如傳統 Modbus/TCP 502 埠不表示協定具備原生身分驗證；`auth_required` 可能描述管理介面、網路閘道或 Modbus Security，不能單靠欄位名稱推論其保護範圍。研究資料必須記錄控制點、設備型號和採集方法。[Modbus Organization 的協定規格清單](https://www.modbus.org/modbus-specifications)列出 Modbus Security 規格。

## 研究問題與可檢驗假說

### RQ1：維護脈絡能否降低設定飄移告警的誤報？

**假說 H1。** 在相同的未核准變更事件檢出率下，加入核准工單、維護窗口、基線版本與設備運轉模式，比純欄位差異產生更少的維護期間誤報。每個變更仍保留紀錄；「經核准」是分類結果，不是刪除證據。對照組為純 JSON 路徑差異；實驗組為路徑差異加核准規則。這呼應 [Sherlock 論文](https://arxiv.org/pdf/2504.06102)將維護事件納入正常運作評估的做法，但 Sherlock 不提供設定快照真值。

### RQ2：跨層證據能否改善事件優先級與解釋？

**假說 H2。** 在設定告警仍獨立輸出的前提下，加入主機／PLC 溯源、協定命令及製程偏差，可提高「有製程影響」事件的排序品質與證據定位正確率。比較設定規則、製程模型、主機與協定訊號，以及經校準的融合方法。[GeCo](https://www.usenix.org/system/files/usenixsecurity25-wolsing.pdf)提供由正常製程時序學習可理解狀態模型的做法；[ProvICS 預印本](https://arxiv.org/html/2607.05989v1)展示主機、PLC、Modbus 和製程資料的同步分析。兩者的研究結果不是本專案設定飄移融合方法的已驗證成效。

### RQ3：方法能否跨設備、版本與場景泛化？

**假說 H3。** 使用語意化欄位映射及明示缺失值，比依賴絕對 IP、暫存器地址與特定設備欄位的模型，在留出設備或版本測試時維持較高的事件檢出率。先在自建測試床做留一設備／韌體版本外測，再以 Sherlock 的場景留出和 ProvICS 的戰役留出評估相應的網路、溯源與製程子模組。公開資料的此類結果只能稱為**子模組泛化**，不能稱為設定飄移泛化。

## 測試床與標註設計

在隔離的 Linux／虛擬 PLC 測試床建立至少兩種設備設定版本，使用唯讀檔案匯出或廠商支援的備份方式取得獨立的目前設定快照。保留核准基線的版本、雜湊、有效區間和責任人角色；保留變更工單的核准狀態、有效設備、欄位、起迄時間。不同來源使用 UTC 時戳，記錄時鐘偏差與採集延遲。不得把從基線物件淺拷貝後修改的值當成「目前設定」。

標註軸分開保存：

1. 設定狀態：未變更、已變更、採集失敗、快照過期、欄位不可見。
2. 授權狀態：經核准、未核准、核准資料缺失或待核實。
3. 後果：未觀察到後果、可觀察網路／製程影響、後果資料缺失。

實驗矩陣至少包含「經核准／未核准」與「有／無可觀察製程影響」的四種組合，另加入維護切換、回滾、短暫網路中斷、快照過期、感測器故障與時間不同步。未觀察到製程影響不等於證明沒有風險。所有變更由測試床操作者依操作程序執行；不對生產 OT 設備進行主動掃描、命令注入或自動修復。

每筆事件至少保存 `event_id`、`device_id`、設定路徑、前後值、基線版本與雜湊、實際快照來源、採集時間、事件起迄、工單識別碼、判斷理由、觀察到的命令／製程證據識別碼。秘密值只存摘要或遮罩，原始敏感資料不放進 Git。

## 階段與交付條件

1. **可重現基線。** 實作結構化設定差異、欄位型別與語意驗證、機器可讀事件；故障和資料缺失與「正常」分開。交付固定樣例和含巢狀欄位、缺失欄位及過期快照的測試。
2. **脈絡規則。** 加入版本化基線、工單及維護窗口；先凍結事件標註與判斷規則，再跑保留測試集。交付每個判斷可追溯的證據鏈。
3. **跨層模組。** 以唯讀方式匯入 Modbus／IEC 104 事件、主機日誌和製程時序，處理時鐘偏差與缺失模態；設定告警本身不依賴製程模型。交付各模態與融合的消融結果。
4. **泛化及壓力測試。** 留出設備、版本、運作情境和完整攻擊／維護事件；報告訓練與推論資源、資料延遲、缺失率和失效案例。交付完整切分清單、參數、程式版本與重現指令。

## 評估規程

主指標為**事件檢出率、每設備日的誤報數、從變更發生到首個告警的延遲、維護事件誤報率**。另外量測設定路徑與證據定位的 precision／recall、優先級校準及資料覆蓋率。先定義告警去重與合併間隔，再評分；對未核准變更，以第一個有效設定快照可見時間作為可偵測起點，同時另報從實際變更時間起算的端到端延遲。對缺失或過期快照分開報告，不將其算成真陰性。[Sherlock 的建議指標](https://arxiv.org/pdf/2504.06102)是偵測到的攻擊、誤報及平均偵測時間；逐點 F1 只作輔助。

先以時間切分同一設備資料，再做留設備、留版本及留場景評估。相同變更工單、攻擊戰役、恢復階段及重疊時間窗不得跨訓練、驗證、測試集合；所有正規化、門檻及欄位映射只用訓練／驗證資料決定。固定資料集版本、時區、切分種子和排除規則，報告事件數與信賴區間。公開資料只評估其實際具備標註的任務，不能用製程攻擊標籤替代設定飄移標籤。
